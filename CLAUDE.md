# Как правильно работать в этом окружении

## Ключевые файлы

- **`docs/printer-status.md`** — канонический статус-документ по обоим проектам (принтер mbot + миграция роутера на OpenWrt). Единственная точка входа: что реально сделано и проверено физически, что осталось, текущее физическое состояние и техника безопасности, живой снимок `printer.cfg`. Читать первым при возврате к любой из задач.
- **`docs/ramps-diagnostics.html`** — большой HTML-гайд (методология, а не текущий статус): установка стека, прошивка MCU, диагностика RAMPS/драйверов, подбор тока/скорости, безопасность 220В, калькулятор Vref, prior art по каждой самодельной методике. Не меняется от сессии к сессии так часто, как `printer-status.md`.
  - Открыть: `docs/serve-ramps.sh` (нужен `python3`/`python` в PATH) поднимает `http.server` на порту 8000 в `docs/` → `http://localhost:8000/ramps-diagnostics.html`. Либо просто открыть файл напрямую (`file://...`).
- **`docs/bom.md`** — спецификация деталей (BOM). Пока только унаследованная от базы MBot Cube механика: моторы, корпус, направляющие. Апгрейд-часть (электроника, стол, экструдер, периферия) не внесена. Внутри — легенда достоверности (подтверждено / вывод из аналога / нужен замер), нарушать её не надо.
- **`docs/purchases.md`** — журнал закупок: что куплено, почём, что досталось с mbot бесплатно, что забыто. Итог считает `scripts/bom-cost.py`, который парсит таблицы прямо из этого файла — цифры итога руками не править, только запускать скрипт.
- **`hardware/`** — исходники деталей собственного изготовления (лазерная резка фанеры, 3D-печать, металл), по каталогу на деталь с карточкой. Принцип: **что делаем сами — исходник лежит здесь, в закупку идёт только сырьё** (лист фанеры, филамент), а не готовая деталь. Правила оформления и индекс — в `hardware/README.md`.
- **`printer-configs/`** — живые конфиги принтера (printer.cfg, moonraker.conf, crowsnest.conf, autotune_tmc.cfg, KlipperScreen.conf, mainsail.cfg), источник истины, см. раздел ниже про правила правки.
- **`scripts/deploy.sh`** — единственный способ выкатить `printer-configs/` на принтер (diff → подтверждение → бэкап на принтере → заливка → restart Klipper → проверка `ready`).
- **`scripts/export-mainsail-ui.sh`** → **`printer-configs/moonraker-db-mainsail-ui.json`** — снимок настроек Mainsail UI (имя принтера, раскладка дашборда, тема), которые пользователь меняет через сам веб-интерфейс, а не через файлы конфига (см. раздел ниже). Только для наглядности/бэкапа, `deploy.sh` этот файл не трогает.
- **`.env`** (в `.gitignore`, не в git) — все секреты (пароли Wi-Fi/SSH).

## Инструмент для shell-команд

**Используй инструмент `Bash` (Git Bash / MSYS2), а НЕ `PowerShell` для всего, что трогает сеть, SSH или запускает вложенные процессы.**

Почему: `PowerShell`-инструмент, вызывающий `C:\cygwin64\bin\bash.exe -lc '...'` как дочерний процесс, надёжно зависает (возвращает пустой результат без ошибки) на SSH и других сетевых/форк-тяжёлых командах — известный класс проблем: Cygwin-процессы, запущенные не-консольным родителем, используют блочную буферизацию консоли и виснут именно на таких вызовах. Простые локальные bash-команды без сети через этот путь работают нормально, но не стоит рисковать — просто используй `Bash`.

`Bash` (Git Bash/MSYS2, появился после установки Git for Windows) работает надёжно и мгновенно для тех же самых SSH-команд — проверено многократно.

**Правило:**
- Bash-инструмент → SSH, curl, git, вообще всё что раньше шло через `bash.exe -lc`.
- PowerShell-инструмент → только чистые Windows-операции (`Test-Path`, `Get-ChildItem`, реестр и т.п.), где не участвует ни один вложенный процесс, трогающий сеть.

Если в новой сессии `Bash`-инструмента нет в списке доступных — значит сессия не увидела Git for Windows (маловероятно, он уже установлен) или инструмент не переобнаружился; в таком случае сначала попробуй ToolSearch по "bash", и если совсем не находится — вернись к PowerShell-обёртке как fallback, но предупреди пользователя.

## Сеть и доступ

- Принтер (Orange Pi, Klipper): `ssh ultra@192.168.11.160` или `root@192.168.11.160`. Пароль — в `.env` в корне репозитория (`PRINTER_SSH_PASSWORD`), в документах его не дублировать. Иногда физически недоступен по SSH/HTTP даже когда отвечает на ping — проверять оба порта (22 и 80) при диагностике, не полагаться на один.
- Домашний роутер (OpenWrt, TP-Link Archer C6 v2): `ssh root@192.168.11.1` — уже настроен ключ (`~/.ssh/id_ed25519`), пароль вводить не должно требоваться.
- Подробности по обоим проектам (принтер mbot + миграция роутера на OpenWrt) — см. `docs\printer-status.md` (рядом с этим файлом), это канонический статус-документ, читать первым при возврате к любой из двух веток.

## Orange Pi — слабое железо, беречь ресурсы (важно, уже ронял принтер)

Это Orange Pi One: 4 ядра H3 и **512 МБ RAM**, без swap-запаса под нагрузку. Он тянет Klipper + Moonraker + KlipperScreen + crowsnest одновременно — свободной памяти в норме остаётся немного.

**Правило: тяжёлую обработку делать на РАБОЧЕЙ МАШИНЕ, а не на принтере.**

Конкретно про скриншоты (самый частый случай — визуальная проверка экрана):

```bash
# на принтере — ТОЛЬКО снять кадр (дёшево):
ssh root@192.168.11.160 'su - ultra -c "DISPLAY=:0 scrot -o /tmp/shot.png"'
scp root@192.168.11.160:/tmp/shot.png ./shot.png
# увеличение/кроп/пиксельный анализ — УЖЕ ЛОКАЛЬНО, не по SSH
```

**Не запускать `convert`/ImageMagick на принтере** (`convert ... -resize 400%`, `-crop`, `txt:-` для пиксельного анализа). Разворот 320x240 в 4x — это несколько десятков МБ в RAM на процесс; несколько таких параллельно (а при работе роя субагентов они идут именно параллельно) съедают память, которой нет.

Что происходит при исчерпании памяти (наблюдалось 2026-07-31, потребовался ручной power-cycle): порты 22 и 80 продолжают **принимать** TCP (ядро живо, сокеты слушают), но ни один демон не отвечает — `sshd` не может форкнуться под сессию и рвёт соединение до отправки версии (`kex_exchange_identification: Connection closed by remote host`), HTTP отдаёт пустоту. Снаружи выглядит как «порт открыт, но всё висит». Лечится только физической перезагрузкой — по SSH зайти уже нельзя.

Профилактика при работе роем субагентов: держать не больше одного агента, реально работающего с устройством (см. очередь-лок в скретчпаде сессии), и не оставлять фоновых циклов, дёргающих SSH по таймеру — они добивают и без того голодающую машину и мешают ей восстановиться.

## Пароли — никогда не вводи их сам

Не печатай/не подставляй пароли в SSH или любые формы аутентификации от лица пользователя, даже если пользователь прямо просит и даёт пароль. Если ключ ещё не настроен и нужен пароль — попроси пользователя ввести его самостоятельно через `!` (команда выполнится в его собственной сессии, вывод попадёт в переписку).

## Секреты не хранить в документах

Пароли, ключи и прочие секреты держать ТОЛЬКО в `.env` в корне репозитория (файл в `.gitignore`, в git не попадает). В `printer-status.md`, `CLAUDE.md`, HTML-гайдах и любых других документах ссылаться на имя переменной (например «пароль — в `.env`, `WIFI_PASSWORD`»), а не писать значение. Требование пользователя, озвучено 2026-07-29 после того, как Wi-Fi-пароль обнаружился открытым текстом в статус-документе. При добавлении новых учётных данных — сразу в `.env`, и проверять, не утёк ли секрет в бэкапы (`*.bak*`) и во временные файлы.

## Конфиги принтера — править ТОЛЬКО здесь, не на самом принтере

С 2026-07-29 `printer-configs/` (printer.cfg, moonraker.conf, crowsnest.conf, autotune_tmc.cfg, KlipperScreen.conf, mainsail.cfg) в этом репозитории — источник истины. Правка конфигов напрямую на принтере по SSH (редактирование `~/printer_data/config/*` руками) **больше не допускается**.

Порядок: правь файлы в `printer-configs/` → закоммить → выкатывай через `scripts/deploy.sh` (он же перезапускает Klipper и ждёт `ready`, см. сам скрипт). Деплой ручной, не по CI/автослиянию в main — причина в `docs/printer-status.md` (стол сейчас греется без полной защиты по 220В, нельзя менять конфиг без присмотра пользователя).

## Настройки Mainsail UI (имя принтера, раскладка дашборда) — отдельный слой, НЕ файловый конфиг

Имя принтера, раскладка виджетов дашборда и тема, которые пользователь настраивает прямо в веб-интерфейсе Mainsail (Settings → General / Dashboard), живут в **базе данных Moonraker** (namespace `mainsail`, отдаётся `GET /server/database/item?namespace=mainsail`), а не в `printer.cfg`/`mainsail.cfg`/`moonraker.conf`. Это отдельный слой хранения от файловых конфигов в `printer-configs/`, и он не покрывается правилом «править только в репозитории» из раздела выше — эти настройки штатно меняются через сам UI.

Чтобы такие изменения не терялись бесследно для истории репозитория: запусти `bash scripts/export-mainsail-ui.sh` — заберёт текущее имя принтера/раскладку/тему из БД Moonraker и запишет точечный снимок в `printer-configs/moonraker-db-mainsail-ui.json`. Это **только снимок для наглядности и бэкапа** — `scripts/deploy.sh` его не деплоит, обратной синхронизации (снимок → БД принтера) нет и не планируется (БД Moonraker — живое состояние, слепой откат небезопасен). Запускать вручную, когда пользователь поменял что-то в Mainsail UI и хочет зафиксировать это в git.
