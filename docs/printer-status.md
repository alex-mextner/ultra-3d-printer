## С ЧЕГО НАЧАТЬ МИНИ-СЕССИЮ (читать это первым)

2. **Не доверяй снимку конфига из этого файла вслепую** — если правишь `printer.cfg`, сначала прочитай живой: `ssh ultra@192.168.11.160 "cat ~/printer_data/config/printer.cfg"`. Снимок ниже актуален на 2026-07-29, но расходится при любой правке.
3. **Правило правки конфига**: перед изменением — `cp printer.cfg printer.cfg.bak.$(date +%Y%m%d%H%M%S)`, после — `curl -X POST .../printer/restart` и обязательно проверить, что вернулось `ready` (а не `error`). Вставляя новый блок — следи, чтобы маркер вставки не разрезал существующую секцию с многострочным телом (уже ловили такую ошибку, см. раздел про макросы стола).

- Хост: Orange Pi One (Armbian), Klipper/Moonraker/Mainsail через KIAUH.

  Путь: `/dev/serial/by-id/usb-FTDI_FT232R_USB_UART_AJV9MLVG-if00-port0` (стабильный, не меняется при смене ttyUSB0/1).
- Драйверы: X/Y/Z — TMC2209 (в панельках RAMPS), подлинные чипы (Trinamic, Германия), sense-резисторы R110 (0.110 Ом, подтверждено визуально). Экструдер — **A4988** (не TMC2209), sense-резисторы подписаны "S1 R100"/"S2 R100" → **0.100 Ом** (подтверждено по маркировке производителя, "S1/S2" = Sense1/Sense2).
  **ВАЖНО: все четыре драйвера работают в standalone-режиме, БЕЗ UART.** Практическое следствие: **ток задаётся ТОЛЬКО физическим триммером Vref на каждом модуле**, значения `run_current` в конфиге ни на что не влияют (секции `[tmc2209 ...]` закомментированы).
  ⚠️ **Численные значения тока в амперах НЕИЗВЕСТНЫ и нигде не записаны.** Причина: у пользователя нет прибора, измеряющего напряжение ниже ~0.5В, а рабочие Vref лежат как раз в этом диапазоне — измерить не получилось. **Токи подбирались чисто эмпирически, по поведению**: крутили триммер, проверяли работу моторов на предельных скоростях и под ручной нагрузкой, останавливались на положении, где нет пропусков шагов и нет перегрева. Формулы (`Vref = ток × 2.5 × 0.110` для TMC2209, `× 8 × 0.100` для A4988) и калькулятор в `ramps-diagnostics.html` остаются справочными — применить их к этой машине не на чем, пока нет подходящего вольтметра.
  Практический вывод для будущих сессий: **не пытаться «восстановить» ток по конфигу или по журналу — их нет.** Если триммер сбился или драйвер заменён — настраивать заново тем же эмпирическим методом (или сначала обзавестись мультиметром/осциллографом, способным читать десятые доли вольта — в гайде описан приём с осциллографом на щупе 1x как обход этой проблемы).
- Камера: USB-веб-камера "XWF-1080P". **НЕ привязываться к номеру `/dev/videoN` — он НЕ стабилен между перезагрузками** (эта ошибка уже ломала камеру, см. «Хаб/питание» п.2a). Камера создаёт два узла (`index0` = реальный поток, `index1` = служебный metadata-узел UVC), плюс отдельно есть узел внутреннего декодера SoC "cedrus" — отсюда путаница с номерами.

- Экструдер: "Dual Drive Extruder", клон BMG-типа. Официальная геометрия Bondtech BMG (на неё ориентируются все клоны): хоббированная (приводная) шестерня диаметром **7.5мм**, реальное передаточное число **50:17** (маркетинговое "3:1" — округление).   rotation_distance: 23.562
  ```ini
  gear_ratio: 50:17
  ```

## UART для TMC2209 — не подключено, это план

**Провода PDN_UART физически НЕ подключены.** Подключение планируется **обычными dupont-коннекторами** в штырьки AUX — там стандартная гребёнка 2.54мм, паять не нужно.

Зачем вообще нужна доработка: стандартный RAMPS 1.4 не имеет разведённого PDN_UART к Mega (в гнезде драйвера на этом месте RESET/SLEEP для A4988, закорочены перемычкой на самой плате).

**Планируемая схема (НЕ смонтирована):**

| Ось | PDN_UART модуля → | AVR pin (Klipper `uart_pin`) | Разъём RAMPS |
|---|---|---|---|
| X | → | PB0 | AUX-3, контакт подписан **D53** |
| Y | → | PL0 | AUX-3, контакт подписан **D49** |
| Z | → | PG1 | AUX-2, контакт подписан **D40** |

Экструдер (A4988) UART не имеет и не должен иметь — не трогать.

**Что это значит для «UART не работает»:** ошибки вида `Unable to read tmc uart 'stepper_x' register IFCNT` / `GCONF`, которые ловили в этой сессии, — **закономерны и не являются загадкой**: секции `[tmc2209 ...]` с `uart_pin` были в конфиге, а физического провода не было вообще. Диагностировать тут нечего, пока провода не подключены. Сейчас `[tmc2209 ...]` закомментированы, все драйверы работают в standalone-режиме (ток — только физическими триммерами Vref), и это полностью рабочее состояние.

**Когда/если захочется UART** (даст программное управление током, `hold_current` для меньшего нагрева в простое, диагностику через `DUMP_TMC`): воткнуть 3 dupont-провода по таблице выше → раскомментировать секции `[tmc2209 ...]` в конфиге → `RESTART` → `DUMP_TMC STEPPER=stepper_x`. Если и тогда не ответит — вот тогда уже диагностика осциллографом по разделу про линию UART в `ramps-diagnostics.html`.

## Прошивка MCU

- Пересобрана и перезалита сегодня, теперь версия хоста и MCU совпадают: `v0.13.0-708-g7046bd00` (Moonraker показывает суффикс `-dirty` из-за локального `.config` в дереве klipper — это нормально).
- Конфигурация сборки: AVR, atmega2560, 16MHz, UART0, 250000 бод, протокол `wiring`. Сохранена в `~/klipper/.config`.
- **Проблема при заливке**: `avrdude` зависал на middle-of-write через USB-хаб — причина в FTDI `latency_timer` (дефолт 16мс) в сочетании с нестабильным хабом. Решение, которое сработало: обойти хаб (подключить кабель Меги напрямую в порт Orange Pi) + выставить `latency_timer=1`:
  ```bash
  echo 1 | sudo tee /sys/bus/usb-serial/devices/ttyUSB<N>/latency_timer
  ```
  **Важно**: это НЕ постоянная настройка — сбрасывается на дефолт 16 при каждом переподключении USB. Для постоянного фикса нужно писать udev-правило (не сделано, некритично, пока хаб не используется для этого порта).

## Хаб/питание — известные проблемы

1. **РЕШЕНО (2026-07-27): USB-хаб больше не нужен вообще.** У Orange Pi One есть второй независимый USB-порт — microUSB с поддержкой OTG host-режима (VBUS через GPIO, штатная возможность SoC). кабель Меги переключён на microUSB-OTG порт (через дешёвый переходник microUSB→USB-A), камера осталась на основном USB-A — теперь это две полностью независимые шины (`lsusb -t`: камера на Bus 001 напрямую, FTDI на Bus 004 напрямую, хаба в топологии нет вообще). Оба устройства подтверждённо работают одновременно (`printer/info: state: ready`, снимок камеры `200 OK`). Старая проблема (хаб ронял оба устройства синхронно, подтверждено по `dmesg`) архитектурно закрыта — докупать хаб с отдельным питанием больше не требуется.
   - Ttyusb-путь в `[mcu] serial:` не изменился и не требует правки — используется стабильный `/dev/serial/by-id/usb-FTDI_FT232R_USB_UART_AJV9MLVG-if00-port0`, а не переезжающий `ttyUSB0/1`, поэтому переезд FTDI на другой физический порт (и смена его номера ttyUSB0→ttyUSB1) никак не задел Klipper.

"команда1 && команда2 && ..."` через `!` в PowerShell-сессии пользователя ненадёжно передавались — команда рвалась на отдельные строки где-то около 70 символов (похоже на перенос строки терминала, превращающийся в реальный `\n`), из-за чего аргументы `cp`/`systemctl` разъезжались и части команды пытались выполниться как отдельные (несуществующие) команды. ## ГЛАВНЫЙ БЛОКЕР СЕССИИ — РЕШЁН (моторы не реагировали, история проблемы и фикса)

- **Полифьюзы F1/F2, возможно, находились в защите** (сработали и держали ток ограниченным) — это состояние самовосстанавливающееся, поэтому позже они и прозвонились целыми.

**Как диагностировали:** мультиметром и проверкой в реальной работе. Осциллограф на этом этапе не применялся.

**ИТОГ: блокер полностью закрыт.** Все четыре мотора (X, Y, Z, extruder) проверены, настроены и работают — направления `dir_pin` выверены через `FORCE_MOVE`, токи подобраны эмпирически, скорости протестированы под нагрузкой (см. «Настройка скорости и тока»). Раздел оставлен только как история проблемы; никаких действий по нему не требуется.

Пин исправлен `PE5`(MIN)→`^!PE4`(MAX), `position_endstop` выставлен на `220` (=`position_max`, так как это MAX-сторона). Смонтирован справа (согласуется с MAX-стороной). ⚠️ **УСТАРЕЛО ДЛЯ X:** 2026-07-28 концевик X передвинут ещё раз, эти значения (PE4/220) больше не описывают реальность — см. «X — переставлен».
- **Z: дополнительно найдена и исправлена инверсия `dir_pin`.** Физический тест через `FORCE_MOVE STEPPER=stepper_z DISTANCE=3 VELOCITY=3` (тест направления, не требует хоуминга — см. ниже про `[force_move]`) показал, что "+3" ехал ВВЕРХ (к соплу) — по конвенции это должно быть уменьшением Z (см. ниже про кинематику), то есть направление было перевёрнуто. Исправлено `dir_pin: PL1` → `!PL1`, повторный тест подтвердил: теперь "+3" едет ВНИЗ, как должно быть.

**Начало координат (0,0,0) для mbot — подтверждено пользователем: спереди-слева-сверху.**

**Направления моторов (dir_pin) — проверено `FORCE_MOVE` по всем ЧЕТЫРЁМ осям, включая экструдер (2026-07-27):**
- X: была без инверсии, нужна инверсия → `dir_pin: !PF1`
- Y: была с инверсией (`!PF7`) — временно снимали по ошибочному отчёту, затем ВОЗВРАЩЕНО обратно на `!PF7` (исходное значение было верным)
- Z: была без инверсии, нужна инверсия → `dir_pin: !PL1`
- Extruder: **физическое движение решено** — ранее `FORCE_MOVE STEPPER=extruder` принимался Klipper без ошибок, но физически не двигал мотор (открытый вопрос, симметричный исходному блокеру сессии). После донастройки Vref мотор уверенно крутит под пальцевой нагрузкой до 50мм/с подачи филамента (см. «Настройка скорости и тока» ниже) — эта часть вопроса закрыта. Направление (что "+" это подача, а не втягивание) НЕ проверялось отдельно визуально/по факту выдавленного филамента — `dir_pin: PA6` (без инверсии) не подтверждён и не опровергнут по направлению, только по факту движения. Проверить перед первой печатью: `FORCE_MOVE STEPPER=extruder DISTANCE=20 VELOCITY=5` с заправленным филаментом, смотреть, выходит ли наружу.

**Кинематика подтверждена пользователем:** стол едет вниз по мере роста Z (Z=0 — стол максимально поднят, ближе всего к соплу), сопло неподвижно по высоте и движется только по X/Y. Z-концевик физически сверху винта = корректно соответствует Z-минимуму. `position_endstop: 0.5` для Z был верным с самого начала, проблема была только в `dir_pin` и полярности концевика, не в этом значении.

**Секция `[force_move] enable_force_move: True` — ОСТАЁТСЯ ПОСТОЯННО (решение 2026-07-29).** Изначально добавлялась как временная, для проверки направлений до доверенного хоуминга — эти тесты завершены. **Но убирать её не нужно и не планируется:** это кастомный принтер, который часто бывает в ремонте/апгрейде (замена хотэнда, перестановка концевиков, смена драйверов), и после каждого такого изменения хоуминг снова становится недоверенным. `FORCE_MOVE`/`SET_KINEMATIC_POSITION` — именно тот инструмент, которым в такой ситуации безопасно двигают ось. Компромисс принят осознанно: эти команды обходят проверку лимитов, поэтому ошибочная `DISTANCE` может увести ось в раму — использовать малые значения.

Ждёт: `G28 Y` / `G28 Z` — после перепроверки Z-концевика (крепление переделано). `G28 X` — только после пересборки `[stepper_x]` под новое положение концевика (хвост №1 в очереди задач).

**Z: TMC2209 в гнезде, UART не отвечает** (`Unable to read tmc uart register GCONF` через `DUMP_TMC`) — **это ожидаемо, а не неисправность: провода PDN_UART физически не подключены** (см. раздел «UART для TMC2209» выше). Решено работать без UART: `[tmc2209 stepper_z]` закомментирован, Z работает как X/Y/E — физический TMC2209 в гнезде, ток через триммер (формула `Vref = run_current × 2.5 × Rsense`, Rsense 0.110 Ом подтверждён визуально).

**Перемычка SPREAD снята на X/Y/Z (TMC2209) — включён тихий режим stealthChop. Экструдер (A4988) НЕ трогали.** Это важное различие: у TMC2209 третья перемычка это SPREAD (режим чоппера, на микрошаг не влияет), а у A4988 та же позиция — MS3, которая микрошаг МЕНЯЕТ. Раз экструдерную перемычку не снимали, у него по-прежнему 1/16. MS1/MS2 (1-я и 2-я перемычки) на всех драйверах остаются на месте — микрошаг 1/16, совпадает с `microsteps: 16` в конфиге. В `printer.cfg` это отражать не нужно и негде: без UART Klipper не видит и не задаёт режим чоппера, это чисто физическая настройка модуля.

**Рассматривалось переключение Freaduino на 3.3В I/O — ОТКЛОНЕНО (см. следующий абзац)** (штатный переключатель на всю плату) — чтобы использовать это для прямого UART Orange Pi↔Мега без внешнего шифтера. Неопределённость: неизвестно точно, транслирует ли переключатель только внешние I/O-пины (тогда сам чип ATmega2560 остаётся на 5В/16МГц, безопасно) или снижает питание всего чипа (тогда 16МГц вне спецификации даташита, которая гарантирует 16МГц только для 4.5-5.5В — риск тонкой нестабильности). Точной схемы платы найти не удалось. Рекомендовано: после переключения проверить мультиметром напряжение прямо на ножке VCC чипа ATmega2560 — если ~5В, транслятор внешний и безопасно; если ~3.3В, чип вне спецификации. Дополнительно потребуется перенастроить Vref на всех драйверах (VDD делителя падает пропорционально, ~×0.66).

**ЭМПИРИЧЕСКИ ПОДТВЕРЖДЕНО (2026-07-27): переключение сломало аналоговую референсную цепь, не только цифровые I/O.** После переключения на 3.3В термисторы `heater_bed` и `extruder` одновременно ушли на -109.28°C (классический признак полностью нерабочего АЦП-измерения, не мелкая погрешность) — Klipper остановился по `not in range`. Это отвечает на открытый вопрос выше: переключатель, похоже, реально садит питание всего чипа (или как минимум его аналоговую часть), а не только транслирует внешние I/O через отдельную микросхему. Решение — **не корректировать конфиг термисторов, а переключить обратно на 5В**. Переключено обратно, показания термисторов вернулись в норму (косвенно подтверждено тем, что стол потом штатно грелся до 120°C). Довод в пользу отдельного внешнего шифтера только для линии UART (не трогая остальную плату) усилился.

**Драйверы X/Y/Z: на этапе диагностики осциллографом временно ставились A4988; сейчас TMC2209 возвращены на место** (см. «Железо» выше). Секции `[tmc2209 stepper_x/y/z]` остаются закомментированными, потому что UART не подключён — ток задаётся триммерами. Это корректное текущее состояние, а не недоделка.

**Прогресс диагностики (2026-07-27), по разработанному гайду `ramps-diagnostics.html`:**
- Полифьюзы F1/F2 — визуально целы, сопротивление ≈0 Ом (это правильное/хорошее значение для предохранителя, не путать с таблицей КЗ по VMOT–GND).
- **D1 — проверен и подтверждён исправным.** Первый замер (с установленной Мегой) дал подозрительно симметричные "десятки кОм" в обе стороны — оказалось паразитная проводимость через обвязку Меги (VIN туда же заведён), а не сам диод. Повторный замер с полностью снятой Мегой дал явную асимметрию: ~0.8 МОм в одну сторону, обрыв/бесконечность в другую — это ожидаемая сигнатура исправного перехода при измерении обычным омметром (не диодным режимом): слабый тестовый ток на нелинейной ВАХ диода даёт кажущееся большое, но конечное сопротивление в проводящем направлении. Отпаивать ножку D1 для изоляции не потребовалось.
- **VMOT проверен на всех 4 гнёздах под напряжением — везде 12В, норма.** Гипотеза "не доходит силовое питание до гнёзд" закрыта, RAMPS в этой части реабилитирована.
- **VDD (5В) проверен на всех 4 гнёздах — тоже норма.** RAMPS полностью реабилитирована по обеим шинам питания (VMOT и VDD); проблема со 100% уверенностью не в плате, а ниже по цепочке — в драйверах, сигналах STEP/DIR/ENABLE или моторах/шлейфах.
- **ЗАВЕРШЕНО:** проверка «драйвер в гнезде» (Мега на RAMPS, драйверы по гнёздам, моторы подключены, подбор Vref) пройдена — все четыре оси в итоге заработали. Дерево решений из гайда пройдено до конца, открытых развилок по этой теме не осталось. По ходу выявлена и устранена единственная аппаратная потеря — сгоревший A4988 (заменён).

## Вентиляторы — текущее состояние

**Три вентилятора, все смонтированы и проверены физически (2026-07-28).**

| # | Назначение | Куда подключён | Секция в Klipper | Чем управляется |
|---|---|---|---|---|
| 1 | Обдув детали | D9 (PH6), MOSFET-выход платы | `[fan]` | Слайсером, `M106`/`M107` |
| 2 | Обдув мотора экструдера | D11 (PB5), разъём SERVOS, **через транзистор IRL640** | `[controller_fan extruder_motor_fan]` | Автоматически: 100% пока запитаны моторы или греет хотэнд, +60с после |
| 3 | Обдув электроники | Отдельный always-on клеммник платы (напрямую от VIN) | нет | Всегда включён, пока подано питание |

Дополнительно: `[temperature_sensor OrangePi_CPU]` — только показывает температуру CPU в Mainsail, **никаким вентилятором не управляет**.

**Почему №2 через транзистор:** D11 находится на разъёме SERVOS — это сырой 5В-логический пин без встроенного MOSFET (в отличие от D8/D9/D10), вентилятор напрямую он не потянет. Смонтирована схема на IRL640 (низкая сторона):

- Gate → резистор 460 Ом → D11 (PB5)
- Source → GND (общий с RAMPS)
- Drain → «минус» вентилятора
- «Плюс» вентилятора → 12В
- Подтяжка Gate→GND (~10 кОм) **сознательно не поставлена** — пользователь счёл некритичным; следствие: при подаче питания вентилятор может кратковременно дёрнуться до инициализации прошивки.
- Радиатор транзистору не нужен: ток вентилятора — сотни мА, IRL640 рассчитан на 17А.

**Транзисторы в наличии:** `IRL640` — логический MOSFET (полностью открывается от 4-5В на затворе, годится для прямого управления с 5В-пина) — **израсходован на этот вентилятор**. `IRF540ZPBF` — несмотря на суффикс «Z», НЕ логический (нужно ~10В на затвор), для прямого управления с 5В-пина не годится, лежит про запас. `KT850A` — биполярный (советская серия КТ, управляется током базы), тоже про запас.

**Именование в Mainsail:** основной `[fan]` — синглтон без параметра имени, его подпись зашита во фронтенде Mainsail и через `printer.cfg` не настраивается (аналогичный open issue есть у Fluidd). Имя `extruder_motor_fan` у `[controller_fan]` — настраивается свободно.

### Охлаждение хотэнда — принятое решение (2026-07-29)

**Вентилятор №2 охлаждает МОТОР экструдера, а не радиатор термобарьера. Отдельного обдува радиатора нет — и это осознанный выбор, а не упущение.**

Обоснование:
- У исходного mbot cube обдув радиатора термобарьера не был предусмотрен конструктивно, и в этой сборке он тоже не делался.
- Вместо этого установлен **мощный (увеличенный) радиатор**, который, возможно, справляется пассивно.
- Проверять это имеет смысл только на реальной печати — до первой длинной печати вопрос остаётся открытым эмпирически, но конструктивное решение принято.

**Как настроен вентилятор мотора:** секция `[controller_fan extruder_motor_fan]` — работает на 100%, пока запитаны моторы (то есть всю печать целиком) или включён нагреватель, плюс ещё 60 секунд после остановки активности. Это то, что нужно именно для охлаждения мотора: привязка к движению, а не к температуре хотэнда.

Почему НЕ `[heater_fan]` (как было изначально): та секция включает вентилятор по температуре хотэнда (>50°C) — правильная логика для радиатора термобарьера, но не для мотора. Мотор греется от тока в обмотках, а не от хотэнда, поэтому логичнее привязка к активности.

<div style="border-left:4px solid #d8a24a;padding-left:12px;margin:12px 0;">

**⚠️ ЕСЛИ ПОЯВЯТСЯ ЗАКУПОРКИ — вот что это значит и что делать.**

Симптом: филамент размягчается ВЫШЕ зоны плавления и закупоривает термобарьер/фидер (heat creep). Проявляется как недоэкструзия ближе к концу длинной печати, щелчки фидера, застрявший филамент. Схема теплового градиента термобарьера (радиатор → шейка → нагревательный блок) — `heatbreak_thermal_gradient.svg` в этой же папке.

Это будет означать, что пассивного радиатора недостаточно. Решение: **добавить отдельный вентилятор обдува радиатора термобарьера** и настроить его как:

```ini
[heater_fan heatbreak_fan]
pin: <свободный пин>
heater: extruder
heater_temp: 50.0
fan_speed: 1.0
```

То есть включается всегда, когда хотэнд горячее 50°C, независимо от движения, и не выключается, пока не остынет. Логика именно такая: пока в горячей зоне есть тепло — его надо отводить от верхней части термобарьера, иначе оно ползёт вверх.

**Не переделывать под эту задачу существующий вентилятор мотора** — это две разные функции с разной логикой включения. Нужен отдельный вентилятор и отдельный пин (свободен D6 или D5 на разъёме SERVOS, но им нужен свой транзистор — см. раздел про подсветку/runout).

1. Первая попытка: D9=деталь, D11=электроника с термостатикой по CPU — неверно, D9 уже был физически занят вентилятором экструдера.
2. Затем: D9=экструдер (как было), D10=нагреватель, свободен только D11 — предложено D11=деталь, электроника always-on без Klipper.
3. Пользователь захотел «как положено» — нашли разъём SERVOS (D4/D5/D6): свободны, но это сырые логические пины без MOSFET, на каждый нужен свой транзистор.
4. По присланному референс-фото платы выяснилось, что есть отдельные always-on клеммники под электронику и под экструдерный вентилятор — отдельно от D9/D10/D11.
5. Пользователь решил, что always-on для экструдерного вентилятора не годится, нужен управляемый → вернулись к D11 + транзистор IRL640 — сначала как `[heater_fan]` (по нагреву хотэнда). Always-on остался только у обдува электроники.

</details>

## ПЛАН (не реализовано, ждёт железа): подсветка + датчик runout филамента

Конвенционные пины на RAMPS 1.4 для обоих — тот же разъём SERVOS (D4/D5/D6), подтверждено по исходникам Marlin (`pins_RAMPS.h`):
- **Подсветка корпуса (case light)** → **D6** (`CASE_LIGHT_PIN` в стоковом Marlin-конфиге при неиспользуемых сервах — это и есть стандартная позиция). В Klipper — простой `[output_pin case_light]`, управление через макрос или `M355`. **Важно**: D6 — сырой логический пин без встроенного MOSFET (как и весь разъём SERVOS) — если подсветка это LED-лента с заметным током, нужен небольшой MOSFET-модуль между пином и лентой; для одиночного маломощного LED через резистор может хватить и напрямую, но пока не решено что именно за подсветка — уточнить при заказе.
- **Датчик runout филамента** → **D4** (`FIL_RUNOUT_PIN` в стоковом Marlin-конфиге — тоже стандартная позиция). В Klipper — `[filament_switch_sensor]`, обычный переключатель (не силовая нагрузка) — никакого MOSFET не нужно, обычный GPIO-вход с подтяжкой, подключается впрямую.
- **D5** (третий пин разъёма SERVOS) остаётся свободным про запас, ничем конкретным не занят по конвенции.

## Макросы для тестирования стола (2026-07-28) — не трогая `[heater_bed]`

`TEST_BED_TEMP TARGET=<температура>` (по умолчанию 120) и `BED_OFF` — обёртки над `SET_HEATER_TEMPERATURE`, добавлены по явной просьбе не редактировать сам тюнинг `[heater_bed]` при каждом новом тесте.

Собственно печать/стол в этот момент не грелись, ничего физически не пострадало — просто Klippy не поднимался. Исправлено: макросы вынесены ПОСЛЕ полного тела `[virtual_sdcard]`, а не сразу за его заголовком. Урок на будущее — при вставке нового блока в существующий `.cfg` через текстовую замену маркера всегда проверять, что маркер не разрезает секцию с многострочным телом.

## Нерешённая проблема — сопло

Сопло физически **не докручивается до конца** в нагревательный блок экструдера (Dual Drive Extruder, см. фото в переписке — стандартный V6-подобный радиатор, синий силиконовый чехол на блоке). Термопасты на резьбе нет — это нормально, не проблема. Подозрение: **несовместимость длины сопла с блоком** (например, длинное "Volcano"-подобное сопло на коротком MK8/V6-подобном блоке) либо PTFE-трубка мешает сесть до конца. **НЕ пытаться докручивать силой** — сорвёт мягкую алюминиевую резьбу блока. Требуется: фото сопла рядом с блоком для точной идентификации совместимости (ещё не прислано).

ИК-термометр показывал большую разницу между блоком и кончиком сопла — вероятно частично артефакт измерения (низкая эмиссивность голого металла сопла vs блок), частично реальный эффект от плохой посадки. Не перепроверено (совет был заклеить кончик матовым скотчем и переизмерить — не сделано).

**Термопаста в хотэнде — уточнено (2026-07-28), полная картина в `ramps-diagnostics.html` (раздел «Термопаста и тепловой барьер», категория «Хотэнд»).** Главное и практически единственное общепризнанное место, где паста реально решает задачу — резьба **радиатор↔термобарьер** (наносится на наружную резьбу термобарьера перед вкручиванием в радиатор): чем эффективнее радиатор охлаждает верхушку термобарьера, тем резче температурный градиент и тем меньше риск heat creep. На картридж/термистор в блоке и на резьбу блок↔сопло — паста опциональна (точность показаний, анти-прикипание при переборке), не критично. На резьбу термобарьер↔блок — не нужна вообще (обе стороны и так горячие). На резьбу сопла — как и раньше отмечено, не нужна и не при чём к проблеме недокручивания (см. абзац выше). Предпочтительный тип — паста на основе нитрида бора (boron nitride): не электропроводна и не деградирует при многократных термоциклах на высоких температурах, в отличие от многих обычных термопаст.

## SSR / heater_bed — работает

**Текущее состояние (2026-07-29):** стол подключён к RAMPS через внешний SSR, `[heater_bed]` + `[verify_heater heater_bed]` в конфиге, **реально прогревался до 120°C и держал температуру**. Магнитная подложка приклеена. Управление — `control: watermark` (bang-bang), `max_temp: 130`, `max_delta: 1.0`.

Для тестов есть макросы `TEST_BED_TEMP TARGET=<t>` (по умолчанию 120) и `BED_OFF` — чтобы не править `[heater_bed]` при каждом заходе.

**Ждёт:** физическое крепление стола на кронштейне рамы mbot — пока не закреплён окончательно.

### Найденные особенности — учитывать при выборе температур печати

- **Разрыв «датчик ↔ реальная поверхность» ~20°C.** При target 80 датчик показывает 80, поверхность — около 60. При target 110 центр поверхности — около 100. Термистор физически ближе к нагревателю, чем к рабочей поверхности, плюс открытая рама постоянно теряет тепло вверх. **Практический вывод: реальный потолок печати — это «показание датчика минус разрыв», а не цифра в конфиге.**
- **Разброс по самой поверхности ~20°C** (при target 110: центр ~100, край ~80). Край активнее отдаёт тепло в воздух. **Поправкой к target это не лечится в принципе** — коррекция применяется к одному числу, а не к зонам; калибровать можно только под одну зону (обычно центр). Не установлено, транзиент это или структурная асимметрия — нужна повторная проверка с длинной выдержкой.
- **Осторожно с ИК-пирометром по голому алюминию:** отдельный замер дал 50°C, но у полированного металла низкая излучательная способность и прибор занижает — цифра недостоверна. Мерить по матовой поверхности либо заклеить пятно матовым скотчем.
- **Возможное улучшение (не сделано):** теплоизоляция между алюминиевой плитой и рамой снизу — уменьшит потери вниз, сократит разрыв и ускорит нагрев.

### Что было починено по дороге (обе проблемы закрыты)

- **`Sensor 'heater_bed' temperature 120.279 not in range 0.000:120.000`** — MCU-шатдаун при подходе к 120°C. Причина: у `watermark` есть `max_delta` — допуск, при котором регулятор сам решает выключиться выше цели. Стояло `target: 120` + `max_delta: 2.0`, то есть контур штатно собирался догреть до 122°C, а `max_temp` (аварийный потолок, проверяется независимо) стоял ровно на 120 — нормальная работа регулятора гарантированно вылезала за аварийный порог. Исправлено: `max_temp` → 130 (запас 10°C, по рекомендациям сообщества 5-10°C), `max_delta` → 1.0.
- **«Стол сам перестаёт греться без команды остановки»** — это был штатный `idle_timeout` Klipper, а не сбой: при отсутствии реальной G-code активности 10 минут (опрос статуса через API не считается) Klipper молча вызывает `TURN_OFF_HEATERS`, без ошибки, `state` остаётся `ready`. Секция `[idle_timeout]` теперь прописана явно, **значение 600с (10 минут, дефолт Klipper)** — временно поднималось до 1800с на время тестов, затем возвращено по просьбе пользователя. Защита от забытого нагрева на месте.

### Ждёт реализации: корректировочная таблица датчик → поверхность

Встроенной возможности в Klipper нет (подтверждено у разработчиков: «not possible as of today»). Неофициальный патч «dual loop PID» (PR #5972) в mainline не влился — патчить ради этого не стоит.

**Практический путь:** написать `[gcode_macro SET_BED_SURFACE_TEMP TARGET=<темп. поверхности>]`, который по калибровочным точкам линейно интерполирует и подставляет реальный target в `heater_bed`. **Собранные точки:** target 80 → поверхность ~60; target 110 → центр ~100. Нужно ещё 1-2 точки (например ближе к 120-130) — с двумя точками интерполяция ненадёжна.

**Стол подтверждён: родной K1 Max, 1000Вт, 110/220В AC (ставить на 220В), термистор NTC 100K/B3950** — совпадает с `Generic 3950` в конфиге ниже, это подтверждённый факт, не предположение (источники: [Spool3D K1 Max Heat Bed Kit](https://spool3d.ca/creality-k1-max-3d-printer-heat-bed-kit/), [FYSETC 100K/3950B для K1/K1 Max](https://www.fysetc.com/products/fysetc-100k-thermistor-and-ceramic-heater-for-creality-k1)). Реальный ток на 220В: 1000/220 ≈ **4.55А**.

Стол — 220В переменного тока, НЕ 12/24В DC — поэтому SSR обязателен архитектурно, не опция: MOSFET-выход RAMPS такое напрямую не коммутирует, только слаботочный триггер на DC-вход SSR. Управление — от выхода D8 RAMPS на DC-вход внешнего SSR; сам SSR своей AC-стороной коммутирует реальный ток стола отдельно от RAMPS.

**⚠️ СТАТУС ОБВЯЗКИ НА 2026-07-29: установлен только сам SSR. Предохранителя на AC-стороне, радиатора на SSR и механического термопредохранителя НЕТ.** Стол при этом уже грелся до 120°C — пока обвязка не собрана, греть только под непрерывным присмотром.

**Обязательно (ничего из этого, кроме SSR, пока не стоит):**
- Предохранитель на AC-стороне SSR под реальный ток — **5-6А** (запас ~25-30% над 4.55А, не больше — избыточный номинал не защитит проводку). F2 RAMPS в этой цепи не участвует.
- SSR-25DA (из исходного плана) — ток стола (4.55А) это лишь ~18% от номинала SSR, с огромным запасом, докупать мощнее не нужно.
- **Радиатор на SSR — обязателен, не опционален (уточнено 2026-07-28).** Кажущийся запас "4.55А при рейтинге 25А" обманчив: тепловыделение в полупроводниковом реле пропорционально току × падению напряжения на переходе (~1-2В), а не проценту от номинала — на 4.55А это ~5-9Вт, ощутимо для голого корпуса без оребрения (по данным с форумов, подлинный SSR-25DA без радиатора комфортен примерно до 5А, заметно греется уже к 8А). Дополнительный риск: SSR-25DA — один из самых часто подделываемых модулей, внутри подделок нередко стоит триак на 12А вместо заявленных 25А при той же маркировке корпуса — если экземпляр окажется поддельным, реальный запас намного меньше, чем кажется по паспортной цифре. Радиатор + термопаста между SSR и радиатором — недорогая страховка для устройства, которое без присмотра коммутирует 1000Вт/220В.

SSR — zero-cross тип, поэтому управление **bang-bang** (`control: watermark`), не PID/ШИМ — zero-cross SSR не может переключаться быстрее ближайшего перехода через ноль сети, из-за чего PID с коротким `pwm_cycle_time` всё равно вырождается в грубое вкл/выкл. Это же поведение по умолчанию у официального `generic-ramps.cfg` в самом Klipper.

**Значения `[heater_bed]` тут намеренно НЕ дублируются** — брать из снимка `printer.cfg` ниже в этом файле. История инцидента со 120/2.0 — в «Что было починено по дороге» выше.

Пины (`PH5`/`PK6`) сверены с официальным `config/generic-ramps.cfg` из репозитория Klipper — это реальная распиновка D8/T1 на RAMPS 1.4 для Mega2560, не путать с более ранним предложенным вариантом от стороннего инструмента (`PC9`/`PC4` — синтаксически невалидные пины для этого MCU, порт C не имеет бита 9 и не подключён к АЦП).

**Дополнительные требования безопасности (полная версия — в `ramps-diagnostics.html`, раздел «Стол на 220В через SSR»), не терять при подключении стола:**
- Механический термопредохранитель (thermal fuse) на столе — аппаратный бэкап, независимый от `verify_heater`: если софт зависнет, а SSR залипнет во включенном состоянии, только он остановит нагрев.
- Перед первым реальным включением — проверить SSR **изолированно**, без подключения к столу и без 220В, что реле переключается по команде и не залипает.
- Развести "грязную" землю силовой части 220В отдельно от логической земли платы/Orange Pi — не смешивать контуры заземления.
- Посчитать реальный ток нагревателя стола (Вт/220В=А), убедиться что он с запасом (не больше 60-70% паспортного) ниже номинала SSR.

## Реальный пиноут TMC2209-модуля (уточнено по фото пользователя, 2026-07-27)

Модуль пользователя — НЕ классический Pololu/A4988-пиноут в мелочах: если сверяться с общими схемами в интернете, есть расхождения. Подтверждено по фото конкретно этого модуля:
- Ряд питания/катушек (соответствует "правой" стороне гнезда RAMPS): `VM(=VMOT) — GND — M2B — M2A — M1A — M1B — VIO(=VDD!) — GND`. То есть на этом модуле пин, который в общих схемах называют VDD, подписан **VIO** — то же самое питание логики.
- Ряд управления: `EN(=ENABLE) — MS1 — MS2 — SPREAD — PDN_UART — PDN_UART — STEP — DIR`. Там, где у A4988 были бы MS3/RESET/SLEEP, здесь `SPREAD` (выбор spreadCycle/stealthChop) и раздвоенный `PDN_UART` (один и тот же сигнал на двух соседних пинах).
- Дополнительно (сбоку, не в основном разъёме): `INDEX`, `DIAG`, `VREF` — отдельные выводы, не участвуют в подключении к RAMPS.
- На планируемое подключение UART (таблица в разделе «UART для TMC2209» → AUX-2/AUX-3 → PB0/PL0/PG1) это не влияет — та таблица составлена по официальной схеме RAMPS, а не по этой картинке. Но при будущем монтаже dupont-проводов и любой визуальной сверке пинов драйвера — использовать эти реальные подписи модуля (`PDN_UART` продублирован на двух соседних пинах), не общую Pololu-схему.

## РЕШЕНИЕ ПО КОНЦЕВИКУ Z — зафиксировано окончательно (2026-07-28)

**Концевик Z остаётся СВЕРХУ винта** (как и было изначально) — это осознанный выбор, не унаследованная случайность, ниже — вся аргументация, почему.

**Исходное сомнение пользователя (правильное по сути):** "стол коснулся концевика — дальше вверх он физически не сможет пойти, в чём смысл?" — то есть казалось, что если концевик срабатывает НА ТОЧНОЙ границе перед соплом, то софт никогда не сможет скомандовать движение чуть ближе для реальной печати (первый слой всегда требует какого-то небольшого дополнительного хода после хоуминга).

**Ключевой факт, снимающий это противоречие:** срабатывание концевика — это НЕ физическая стена. Klipper проверяет пин концевика ТОЛЬКО во время самого хоуминга — после хоуминга обычные G1-команды могут спокойно продолжить движение в ту же сторону (например, с Z=0.5 на Z=0.2, то есть чуть ближе к соплу, чем точка срабатывания). Физически это возможно ТОЛЬКО если у концевика/его крепления есть реальный запас хода ПОСЛЕ точки срабатывания — либо рычаг микрика может продавиться ещё немного, либо флажок на каретке проезжает мимо датчика и катится дальше. Без этого запаса схема правда не работала бы — сомнение пользователя было физически верным, просто конкретно у стандартных концевиков (рычажный микрик, флажок-мимо-датчика) такой запас закладывается конструктивно.

**Почему не концевик снизу (Z-MAX, подальше от сопла):** физически некуда ставить (нет места на раме под механизм). Более широко — это была бы БЕЗОПАСНЕЕ схема (хоуминг происходит вдали от сопла, риска столкновения при самом хоуминге вообще нет), но её главный недостаток — реальная точка отсчёта далеко от рабочей зоны, любая ошибка/люфт по всему ходу винта накапливается сильнее, чем при хоуминге рядом с рабочей зоной. Учитывая, что физически негде разместить — вопрос закрыт, остаётся top-вариант.

**Почему не sensorless homing (StallGuard TMC2209) вместо концевика вообще:** официальная документация Klipper прямо не рекомендует sensorless homing для Z — по двум причинам: (1) точность — StallGuard не даёт чёткую стоп-точку, мотор проезжает ещё несколько шагов после реального застревания прежде чем это будет зафиксировано, задержка зависит от тока/скорости/температуры — для Z (где первый слой чувствителен к долям мм) это плохо; (2) механика — Z обычно медленная и высокомоментная (винт с редукцией), а StallGuard нужна ДОСТАТОЧНАЯ скорость для надёжного срабатывания — именно там, где Z работает хуже всего. Плюс требует UART (сейчас не работает) и реального физического "впечатывания" в жёсткий упор на винте при каждом хоуминге — механический износ со временем. Официальный совет комьюнити: для Z обычный концевик надёжнее.

**Итоговое решение и почему оно решает и практическую проблему (частая смена железа):** оставить концевик сверху, но **сделать крепление регулируемым по высоте** (паз + винт, гайка в напечатанном гнезде, барашек для быстрой регулировки без инструмента — обсуждали механику отдельно). Это даёт: (а) безопасную, повторяемую точку отсчёта при хоуминге — как и раньше; (б) грубую механическую подстройку под конкретную комбинацию сопла/хитблока/стола одним движением паза; (в) точную подгонку зазора под первый слой — по-прежнему через software Z-offset (`SET_GCODE_OFFSET`/бумажный тест) при каждой смене железа, паз не пытается заменить эту точность, только держит концевик в разумном безопасном диапазоне.

**Сделано физически (2026-07-28, со слов пользователя):** крепление Z переделано на регулируемое по высоте. Z endstop_pin/position_endstop в текущем `printer.cfg` (`^!PD3`, `position_endstop: 0.5`) — это значение НЕ обязательно всё ещё верно после переделки крепления, нужно перепроверить `QUERY_ENDSTOPS` + аккуратный джог перед следующим `G28 Z`, не доверять старому числу автоматически.

## ПЛАН: экран + 5 кнопок навигации на Orange Pi (2026-07-28 план → 2026-07-30 РЕАЛИЗОВАНО)

Задумано на время ожидания креплений стола/деталей экструдера. Экран — 2.2" SPI TFT 240x320 (чип ILI9341, есть SD-модуль на плате, скорее всего не понадобится). Кнопки — примитивный 5-контактный модуль: up/down/left/right/center + общий GND (без чипа/шины, просто микрокнопки на GND).

**Ключевое архитектурное решение: и экран, и кнопки — на GPIO самого Orange Pi, НЕ на RAMPS/Mega.** Причина: Klipper's `[display]` (штатное меню на MCU) поддерживает только определённые контроллеры (`hd44780`, `st7920`, `ssd1306`/`sh1106`, `uc1701`, `aip31068_spi`) — ILI9341 туда не входит, готового драйвера в Klipper для него нет. Вместо этого экран поднимается как обычный Linux-framebuffer через SPI (штатный путь для SPI TFT на Armbian/одноплатниках), а поверх рисует любой GUI — то есть по смыслу это уже не про Klipper-прошивку MCU, а про сам Orange Pi. Раз экран целиком на стороне Orange Pi — кнопки логично вешать туда же, не гонять сигнал через RAMPS.

**Шаги:**
1. **Включить SPI на Orange Pi.** `armbian-config` → System → Hardware → SPI-spidev → Save → перезагрузка (тот же механизм, что уже использовался для UART3 ранее в этом проекте).
2. **Использовать SPI0, не SPI1** — важный нюанс именно для этого чипа (Allwinner H3): SPI1 физически делит пины с UART3 (пины 8/10 на 40-pin гребёнке, PA13/PA14) — тот самый UART3, который рассматривался (но не был реализован) для прямого UART Orange Pi↔Mega ранее в этом проекте. Если использовать SPI1 для экрана — дорога к UART3 в будущем закрывается. SPI0 живёт на отдельных пинах (19/21/23/24 = PC0/PC1/PC2/PC3, MOSI/MISO/CLK/CS) и ничего не делит — оставляет UART3 свободным на будущее, хотя актуальность самого UART3-плана и так снизилась после фикса камеры через OTG.
3. **Экран через device-tree overlay (`fbtft`/`ili9341`)** — превращает SPI-панель в `/dev/fbN`. Кроме 4 пинов SPI0 нужны ещё 3 GPIO: DC (data/command), RESET, LED/подсветка — любые свободные пины с 40-pin гребёнки (не проверено, какие конкретно свободны помимо SPI0/уже занятых — сверить по полной распиновке Orange Pi One перед монтажом).
4. **UI поверх framebuffer — KlipperScreen с `keyboard_navigation: true`** (секция `[main]` конфига KlipperScreen). Официально поддерживается, НО в документации прямым текстом: "UI is coded to be touchscreen controlled, this is not recommended as the only way to control" — то есть реально работает, но не так отполировано, как тач. Стоит воспринимать как рабочий, но не идеальный путь — тестировать по факту, не ждать идеальной эргономики с первой попытки.
5. **Кнопки — через `gpio-keys` device-tree overlay**, а не через самописный поллинг-скрипт: это штатный механизм ядра Linux, превращающий физические GPIO-кнопки в обычные события клавиатуры (`evdev`), которые KlipperScreen's `keyboard_navigation` потребляет как есть. Маппинг: up/down — впрямую, center → Enter, left → Tab-назад/back, right — либо второй Tab-вперёд, либо на будущее под кастомную функцию.
6. **Долгое удержание → кастомные макросы** (задумано пользователем) — `gpio-keys` сам по себе даёт только press/release события, не длительность. Для "удержание = другая функция" нужна отдельная логика поверх (например: демон на Orange Pi, который меряет длительность press/release через `evdev` и по таймауту шлёт другой gcode/команду через Moonraker API, чем короткое нажатие) — не штатная фича «из коробки», а небольшая самописная обвязка. Не браться за это, пока не заработает базовая навигация.
7. **Ещё не сделано и не проверено:** полная распиновка Orange Pi One 40-pin (какие конкретно GPIO свободны под DC/RESET/LED и подтверждение, что кнопочные пины не конфликтуют ни с чем) — сверить по официальной распиновке (linux-sunxi.org / GitHub `cagritrk/OrangePi.GPIO_Examples`) перед физическим подключением.

**Итог по приоритету на время ожидания:** можно уже сейчас (1) включить SPI0 через armbian-config, (2) свериться с полной распиновкой под DC/RESET/LED/кнопки, (3) попробовать поднять `/dev/fbN` через dtoverlay и убедиться что экран вообще откликается — это не требует новых деталей, кроме того что уже есть. KlipperScreen+кнопки — уже второй этап, после того как framebuffer заработает.

Уменьшение размера самих кнопок (`set_size_request`) эффекта не дало — раздутие шло от колонки списка температур, а не от кнопок. - Живьём проверено: (1) пиксельный анализ скриншота (ImageMagick `convert ... txt:-`, уже стоит на принтере) — до фикса ровно 4 цветные полосы видны, 5-я обрезана по x=319; после фикса все 5 (Move/Temperature/Extrude/More/Print) видны в одном ряду от края до края; (2) список температур читается полностью, без обрезки имён; (3) график виден в правом верхнем углу (сетка, линия тренда, ось Y); (4) клавиатурная навигация (физические стрелки через `xdotool`, быстрая серия в одной SSH-сессии) корректно проходит по всем 5 кнопкам слева направо, останавливается на краях, не перепрыгивает; (5) `Return` на кнопке "Temperature" реально открывает панель Temperature (не просто подсвечивает), `BackSpace` корректно возвращает на главный экран.
- Компромисс: график узкий (~77-80px) — фундаментальное ограничение бюджета 320px экрана при требовании не обрезать имена температур (~205px список + ~32px сайдбар оставляют мало места). Не переоткрыто как проблема — пользователь просил только позицию (top-right), не конкретную ширину.

## Дозаказать / докупить (актуализировано 2026-07-29)

**Для 220В-обвязки стола** (стол уже работает, но обвязка не полная):
- ✅ Термостойкий силиконовый провод под 220В — уже правильный, есть.
- ✅ Предохранитель + держатель — не нужно докупать отдельно, нашёлся встроенным в корпусной IEC-разъём 220В (там же и выключатель питания — бонус).
- 🕓 Радиатор для SSR — заказан, едет с термоклеем (не термопаста, но для SSR-радиатора это ок).
- ✅ Механический термопредохранитель — взят на **133°C** (осознанный компромисс: 120°C — практический предел, к которому редко подходят вплотную; пользователь не хочет более высокий номинал (150-180°C), чтобы в случае реального перегрева не испортить магнитную подложку стола). Разумнее исходного заказа на 121°C, но запас всего ~13°C держится только если PID стола откалиброван — сейчас `pid_Kp/Ki/Kd` в `printer.cfg` ещё дефолтные (не под реальную тепловую массу этого стола), а без калибровки нагрев может давать заброс на несколько градусов выше уставки при выходе на температуру, что съедает часть запаса непредсказуемо. **Перед тем как полагаться на этот предохранитель — прогнать `PID_CALIBRATE HEATER=heater_bed TARGET=120` (или на реальную рабочую температуру) и записать `pid_Kp/Ki/Kd` в конфиг.** Также при монтаже не лепить предохранитель вплотную к самому горячему участку нагревателя — иначе он видит температуру выше, чем показывает термистор, даже в штатном режиме.
- ⬜ Переходная пластина под крепление стола к раме mbot — всё ещё не куплена.

**Электроника:**
- IRL640 (для подсветки, второй экземпляр) заменён на план: **IRLZ44N** (или IRLB8721 как альтернатива) — тоже TO-220, тоже логический уровень (открывается от 5В RAMPS-пина без изменений в схеме), но на порядок дешевле и продаётся массово/наборами, в отличие от дорогого поштучного IRL640. Брать сразу несколько штук (подсветка + сирена, см. ниже + запас) — при такой цене за штуку роли не играет.
- ✅ Runout — покупать не нужно, будет собран самостоятельно из уже имеющегося концевика с длинной лапкой.
- ✅ Провода/шлейфы под экран и кнопки — куплены и разведены, экран и кнопки физически подключены и работают (2026-07-30, см. «ПЛАН: экран + 5 кнопок навигации»).

**Датчик дыма — решено интегрировать в Klipper (не просто "на всякий случай"):**
- Модуль **MQ-2** (общий дым + горючие газы: LPG/метан/водород/спирт) — в корзине. MQ-4 намеренно не берём, он заточен под метан/природный газ и для этой задачи не подходит. Если захочется подстраховаться вторым сенсором — логичная пара MQ-2 + **MQ-7** (угарный газ, отдельная опасность при тлеющей проводке), а не MQ-2 + MQ-4.
- План интеграции: цифровой выход **DO** платы MQ-2 (компаратор + подстроечный порог прямо на плате, ADC не нужен) → свободный цифровой пин → Klipper `[gcode_button]` → макрос: `TURN_OFF_HEATERS` + `M112` + включение сирены.
- **Сирена** — активный 12В зуммер/сирена-модуль, включается тем же типом MOSFET (IRLZ44N), тем же макросом (`SET_PIN`) — дублирует штатный писк/светодиод на самой плате MQ-2, чтобы было слышно из другой комнаты.

**По желанию:** филамент, если не под рукой.

**Перед первой реальной печатью (не забыть):** проверить пучок проводов на каретке X (спиральная оплётка) — не пережимает ли PTFE-трубку, не трётся ли изоляция в точке выхода из экструдера; натяжение ремней и перпендикулярность гантри.

## Идеи на будущее (не решено, просто зафиксировано 2026-07-29)

- **Проверка чистоты стола перед печатью (простое CV, без нейросетей):** Orange Pi One слишком слаб для реальных нейросетей (4×A7, обычно 512МБ ОЗУ, и так занят Klipper/Moonraker/crowsnest), но для задачи "нет ли на столе волоса/мусора/инструмента" нейросеть и не нужна — снять эталонный снимок чистого стола, перед стартом печати (или между слоями) сравнивать со снэпшотом (`.../webcam/?action=snapshot`) через простой diff/контуры (OpenCV), при превышении порога — предупреждение или блок старта. Это реально тянет сам Orange Pi One, доп. железо не требуется.
- Если захочется полноценную модель (классифицировать что именно за предмет, устойчивость к освещению) — Orange Pi для инференса не годится. Варианты: гонять инференс на своём Windows-ноуте по той же локалке (снэпшот с камеры принтера тянется по LAN, ничего не платится и никуда наружу не уходит), либо Oracle Cloud Free Tier (по-настоящему бессрочно бесплатные ARM-инстансы до 4 ядер/24ГБ — хватит на лёгкую модель типа YOLOv8n). Google Colab для этого не подходит — он про интерактивные ноутбуки, не про постоянно доступный сервис по запросу.
- **Мониторинг сбоев печати ("спагетти", отклеившаяся деталь) — не изобретать своё:** существует готовый opensource-проект **Obico** (бывший The Spaghetti Detective), self-hosted вариант + интеграция с Klipper/Moonraker, есть бесплатный AI-детект на их сервере. Закрывает именно "во время печати", а не "чисто ли стол перед стартом" — это разные задачи, diff-скрипт выше для второго.
- **Одна RGB-лента (уже есть, не адресная, не WS2812 — Klipper-нативный `[neopixel]` тут не подходит, это только для адресной WS2812 с одним data-проводом) на две роли сразу:** статус цветом + подсветка рабочей зоны. 3 канала `[output_pin]` с PWM (по каналу на R/G/B), каждый канал — свой MOSFET (тот же IRLZ44N, 3 штуки). Макрос выставляет цвет под статус: греется/готово/ошибка — свои цвета, а **"печатает" = R=1,G=1,B=1 (белый)** — так подсветка рабочей зоны включается сама именно во время печати, когда она и нужна, плюс бонус — камера видит печать при нормальном свете, а не в полумраке. Вторая лента не нужна.
- Уведомления в Telegram через Moonraker (готовый плагин `moonraker-telegram-bot`) — конец печати/ошибка/срабатывание датчика дыма прилетает в телефон, а не только сиреной в комнате.
